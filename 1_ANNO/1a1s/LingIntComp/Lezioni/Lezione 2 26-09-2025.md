# Struttura di un compilatore

Questa qui sotto è una vista ad alto livello del compilatore

![[Pasted image 20250928120113.png]]

Un compilatore ha dei determinati requisiti:
- Il compilatore deve distinguere i programmi validi da quelli non validi
- Il compilatore deve generare codice corretto, rispettando la semantica del codice sorgente. Questo un punto un po' articolato per via delle varie ottimizzazioni che il compilatore esegue durante la fase di compilazione. 
- Deve gestire le risorse in modo efficiente
- Deve interagire col sistema operativo (linking dinamico delle librerie)

Gli errori lanciati del compilatore sono errori per cui è impossibile generare il codice macchina in M
I warning possono diventare errori e il compilatore lo segnala come un avviso.

# Compilatore a due passi
![[Pasted image 20250928121355.png]]

- Front-end: si occupa delle dipendenze per il linguaggio L
- Back-end: si occupa delle dipendenze della macchina target.

È possibile avere più front-end e più back-end.

Linguaggio IR: rende indipendente il front-end dal back-end e deve poter rappresentare le informazioni raccolte dal compilatore, esistono vari formati di linguaggi IR.
Le varie tipolgie di linguaggi IR sono:
- Strutturali: alberi, grafi, DAG
- Lineari: 3-address code, stack-machine code
- Ibridi: CFG (Control Flow Graph) per BB (Basic Block)

Le soluzioni ibride uniscono i pro delle strutturali e lineari.
Esempi: 
- GCC -> RTL(Register Transfer Language)
- LLVM -> LLVM Bitcode

# Front-end del compilatore

Il front-end deve prendere in input un linguaggio L e produrre il corrispettivo in linguaggio IR.
Segnala warning ed errori facilmente riconoscibili. 
Deve riconoscere programmi validi e non validi.
L'IDE non c'entra nulla con il front-end, è solo un text editor più sofisticato.

Il front-end è composto da:

![[Pasted image 20250928122532.png]]

- Lexer: Si occupa di analisi lessicale, prende in input un file con una sequenza di caratteri, deve essere efficiente, produce una sequenza di tokens.
- Parser: Esegue l'analisi sintattica, libera da contesto prende la sequenza di token e genera l'IR
- Checker: controlla che le frasi scritte siano sintatticamente corrette e semanticamente corrette, dipendente da contesto. Operazioni come: x+y, ++x, x-y dipendono dal contesto.


# Lexer, detti anche scanner
Si occupa di analisi lessicale.
Come detto precedentemente prende in input una sequenza di caratteri e produce dei token:
TOKEN: è una coppia (part of speech, lessema).
Esempi: (FLOAT, 3.1415), (KWD, while)
In questo caso FLOAT e KWD sono dei classificatori che indicano il tipo della sequenza dei caratteri.

Problema della specifica: Come definire la correttezza in modo rigoroso dei token? Si usa un linguaggio di espressioni regolari (RE), meglio comprensibile per l'umano.

Quando si passa all'implementazione si deve tenere conto di ottenere un ottima efficienza poiché bisogna leggere una sequenza di caratteri. 


# RE per identificatori
### Specifiche:
- DIGIT = [0-9]
- LETTER = [a-zA-Z] | [\_]
- ID = LETTER(LETTER | DIGIT)*

"0, 9", "a zA Z" sono il linguaggio che voglio descrivere
"[ ]", "-" sono il metalinguaggio.
Un meta linguaggio è un linguaggio che permette di descrivere altri linguaggi.

### Implementazione
Si usano i DFSA (Automi a stati finiti deterministici). L'efficienza del lexer gioca un ruolo fondamentale.

# Parser
Si occupa di analisi sintattica.
Prende in input la sequenza di token dal lexer e produce in output l'IR della struttura sintattica.
L'output deve essere adeguato per le fasi successive:
- Concrete Syntax Tree, usato raramente perché troppo complessi con molti dettagli
- AST (Abstract Syntax Tree)

Il parser può lanciare errori/warning.
### Specifiche
- Linguaggio adeguato: CFG (Context Free Grammar)
- Comprensibile dal progettista (essere umano)
- Problemi non banali (determinismo, efficienza e ambiguità)

### Implementazione
Come riconoscitore di usa un PDA (Automa a pila non deterministico)
Viene generato automaticamente partendo dalla grammatica.
